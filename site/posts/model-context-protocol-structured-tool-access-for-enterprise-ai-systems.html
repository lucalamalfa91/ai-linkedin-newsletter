Model Context Protocol (MCP)

Model Context Protocol: Structured Tool Access for Enterprise AI Systems

MCP standardizes how language models discover and call external tools — here is what that means in practice.

July 23, 2026

Model Context Protocol (MCP) is an open specification that defines a standard wire format for exposing tools, resources, and prompts to a language model host. Instead of every team writing bespoke function-calling glue code for each model and each data source, MCP gives you a client-server contract: the host (your LLM runtime) speaks to one or more MCP servers, each of which advertises a capability manifest and handles JSON-RPC calls at runtime. The model never talks to your database directly — it talks to the protocol, and the server mediates everything. That separation is the point.

For an AI Architect designing enterprise systems, this matters for a specific reason: tool sprawl. In a typical agentic build you end up with a dozen ad-hoc integrations — a Slack wrapper here, a SQL executor there, a PDF reader bolted on — each with its own auth pattern, error contract, and retry logic. MCP forces you to think about each integration as a declared service with a schema. That means you can version it, test it in isolation, swap the underlying implementation without touching the agent, and audit exactly what the model was allowed to call in any given session. Observability and access control become first-class concerns instead of afterthoughts.

The catch is operational overhead. Every MCP server is a process you now have to run, monitor, and secure. In a local developer setup that is fine. In a multi-tenant enterprise deployment you are suddenly managing a sidecar fleet, and the latency of an extra network hop per tool call adds up inside tight agentic loops. There is also a subtler failure mode: because MCP makes it easy to expose many tools, teams tend to expose too many. A model presented with forty tools in its context window performs noticeably worse at tool selection than one presented with eight. The protocol does not solve the curation problem — you still have to make hard choices about what the model should be allowed to see.

The discovery mechanism is worth understanding before you commit to it. At session start the host sends an initialize request; the server responds with its declared tools, resources, and supported protocol version. From that point, every tool invocation is a tools/call JSON-RPC request with a named tool and a typed argument payload. The server executes and returns a structured result or a typed error. That lifecycle is simple enough that you can implement a compliant server in an afternoon — but simple does not mean trivial to operate at scale, especially when you need per-request auth context flowing through the call.

How I use this every day

Before I wire any new data source into an agentic system, I write the MCP server manifest first — the tool names, their input schemas, and the error types — and review it with the client team before a single line of implementation exists. That manifest review is where we cut tools down to the minimum viable set: if we cannot explain in one sentence why the model needs that specific tool, it does not go in. I also run the manifest through a quick token count, because the tool descriptions land in the context window and I want to know the overhead before the first integration test, not after I see latency regressions in staging.

Example projects

modelcontextprotocol/servers — Reference implementations and community MCP servers.

I use the reference server implementations as a baseline audit — I read their tool schemas before writing my own to make sure I am not reinventing patterns the spec already solves.

python

from mcp.server.fastmcp import FastMCP
from mcp.types import TextContent
import httpx

mcp = FastMCP("internal-docs")

@mcp.tool()
async def search_docs(query: str, max_results: int = 5) -> list[TextContent]:
    """Search the internal knowledge base. Returns ranked text snippets."""
    async with httpx.AsyncClient() as client:
        resp = await client.get(
            "https://kb.internal/api/search",
            params={"q": query, "limit": max_results},
            headers={"Authorization": "Bearer ${KB_TOKEN}"},
            timeout=8.0,
        )
        resp.raise_for_status()
        hits = resp.json()["hits"]
    return [
        TextContent(type="text", text=f"{h['title']}\n{h['excerpt']}")
        for h in hits
    ]

if __name__ == "__main__":
    mcp.run(transport="stdio")
