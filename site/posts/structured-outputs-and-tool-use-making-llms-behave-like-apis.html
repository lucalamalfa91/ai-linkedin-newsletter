Structured Outputs and Tool Use: Making LLMs Behave Like APIs

How to design LLM tool interfaces and structured outputs that hold up inside real enterprise systems.

July 22, 2026

Structured outputs and tool use are two sides of the same coin. Structured outputs constrain what the model returns — a JSON schema, a typed object, a predictable envelope — so downstream code can parse it without brittle regex. Tool use (function calling) goes the other direction: you give the model a declared interface, and it decides when and how to invoke it, passing back arguments you can execute. Together they let you treat an LLM as an orchestrator rather than a text generator, which is the shift that makes agents practical rather than demo-ware.

From an architecture standpoint, the reason this matters is reliability under composition. A single LLM call that returns freeform prose is fine for a chatbot. The moment you chain three or four calls together — retrieval, reasoning, action, summarization — unstructured outputs cascade failures downstream. If step two cannot parse step one's response, your agent halts or, worse, silently continues with garbage. Defining strict schemas at every handoff is the equivalent of typing your function signatures: it surfaces contract violations at the boundary rather than three layers deep in a stack trace.

The catch is that schema strictness and model capability trade off against each other in non-obvious ways. Very tight schemas — deeply nested objects, many required fields, strict enums — can cause the model to hallucinate values just to satisfy the shape, especially on smaller or quantized models. I have seen production systems where enforcing a 12-field JSON schema caused the model to invent plausible-sounding but wrong values for optional fields rather than omit them. The fix is usually to make optional fields genuinely optional, add a free-text reasoning field the model can use as scratch space, and validate outputs against business rules separately from schema validation. Schema compliance and semantic correctness are not the same thing.

Tool design has its own failure mode: tool proliferation. When you give a model 30 tools, retrieval of the right one degrades — the model either picks the wrong tool or calls multiple tools redundantly. The discipline is to design tools like Unix commands: small, single-purpose, composable. A search_contracts tool and a summarize_document tool beat a single handle_contract_query tool every time, because the model can reason about what each does without ambiguity. Name them like functions you would actually write, not like features in a product spec.

How I use this every day

My default rule: every LLM call that feeds into another system component gets a response schema defined before I write a single line of prompt. I open a Pydantic model first, sketch the fields, then write the prompt around it — not the other way around. For tool definitions I keep a personal checklist: each tool must have a name that reads like a Python function, a docstring the model will actually see, and no more than four parameters. If I find myself adding a fifth parameter, that is a signal the tool is doing two things and needs to be split. When I hand off a new agent design to a client team, I run a quick adversarial test: I ask the model to call each tool with deliberately ambiguous input and check whether it picks the right one or halts and asks for clarification — that single test reveals most tool-naming and schema problems before they hit production.

Example projects

anthropics/claude-cookbooks — Tool-use and structured-output recipes (calculators, SQL, customer service agents).

I reach for the Claude cookbooks when I need a concrete, already-debugged pattern for a specific tool-use scenario — the SQL and customer-service agent recipes save me from reinventing the schema and prompt structure every engagement.

python

import anthropic
import json

client = anthropic.Anthropic()

tools = [
    {
        "name": "run_sql_query",
        "description": "Execute a read-only SQL query and return rows as a list of dicts.",
        "input_schema": {
            "type": "object",
            "properties": {
                "query": {"type": "string", "description": "Valid SELECT statement"},
                "limit": {"type": "integer", "default": 50}
            },
            "required": ["query"]
        }
    }
]

response = client.messages.create(
    model="claude-opus-4-5",
    max_tokens=1024,
    tools=tools,
    messages=[{"role": "user", "content": "How many invoices are overdue by more than 30 days?"}]
)

for block in response.content:
    if block.type == "tool_use":
        print(f"Tool: {block.name}")
        print(f"Input: {json.dumps(block.input, indent=2)}")

modelcontextprotocol/servers — Reference MCP server implementations that expose tools to LLMs.

I use the MCP reference servers as a baseline when wiring a client's internal data sources into an agent — they give me a spec-compliant server skeleton so I spend time on business logic rather than protocol plumbing.

python

# Minimal MCP server exposing a single read-only tool
# Based on the modelcontextprotocol/servers reference pattern

from mcp.server import Server
from mcp.server.stdio import stdio_server
from mcp.types import Tool, TextContent
import asyncio

app = Server("contracts-db")

@app.list_tools()
async def list_tools() -> list[Tool]:
    return [
        Tool(
            name="search_contracts",
            description="Full-text search over active contracts. Returns title, counterparty, expiry.",
            inputSchema={
                "type": "object",
                "properties": {
                    "query": {"type": "string"},
                    "max_results": {"type": "integer", "default": 5}
                },
                "required": ["query"]
            }
        )
    ]

@app.call_tool()
async def call_tool(name: str, arguments: dict):
    if name == "search_contracts":
        # Replace with real DB call
        results = [{"title": "MSA - Acme AG", "expiry": "2026-03-31", "counterparty": "Acme AG"}]
        return [TextContent(type="text", text=str(results))]

async def main():
    async with stdio_server() as streams:
        await app.run(*streams, app.create_initialization_options())

if __name__ == "__main__":
    asyncio.run(main())
