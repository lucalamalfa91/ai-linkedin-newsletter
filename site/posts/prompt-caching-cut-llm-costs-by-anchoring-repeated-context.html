Prompt Caching: Cut LLM Costs by Anchoring Repeated Context

Learn how to structure prompts so repeated context is cached and billed once, not on every call.

July 21, 2026

Prompt caching is a billing and latency optimization offered by providers like Anthropic where a prefix of your prompt — the system prompt, a large document, a few-shot example block — is stored server-side after the first request. Subsequent calls that share that exact prefix are charged at a fraction of the normal input token rate (roughly 10% with Anthropic's current pricing) and return faster because the KV cache is already warm. The key constraint: the cached prefix must be byte-for-byte identical across calls, which means your architecture has to be intentional about what goes where in the prompt.

For an AI Architect designing enterprise systems, this matters most when you have a large, stable context that gets reused across many user turns or parallel requests — a 50-page policy document used for Q&A, a dense system prompt encoding a persona and rules, or a fixed few-shot library. In those patterns, input tokens dominate your cost curve. A RAG pipeline that stuffs 8,000 tokens of retrieved context into every call, for instance, can see 80–90% of its token spend evaporate once caching is properly structured, simply by front-loading the stable material and keeping the dynamic user query at the tail end of the prompt.

The main failure mode is cache invalidation by accident. Any change to the bytes before the cache breakpoint — a timestamp injected into the system prompt, a user ID interpolated early in the template, even a whitespace difference from a template engine — resets the cache and you pay full price. I've seen teams instrument caching, celebrate the savings in staging, then watch costs spike in production because a logging middleware was prepending a request trace ID to every system prompt. The discipline required is treating your prompt prefix like an immutable artifact, not a template. A secondary trade-off: cache entries have a TTL (currently five minutes of inactivity on Anthropic), so low-traffic endpoints may never actually hit cached state — you need to model your request rate before assuming savings will materialize.

How I use this every day

My default rule when scoping any feature that calls an LLM more than once per user session: I draw a line through the prompt and ask 'what above this line never changes between calls?' — everything above that line becomes a candidate for a cache block. I then add Anthropic's cache_control marker at that boundary and check the response metadata for cache_read_input_tokens in the first few test runs. If I see zeros there after the second call, something is invalidating the prefix and I start diffing the raw serialized prompt bytes across requests before touching anything else. For clients with infrequent traffic I skip caching entirely and invest the same effort in reducing prompt length instead, because a cache that never warms is just added complexity with no return.

Example projects

anthropics/claude-cookbooks — Includes worked examples of prompt caching to cut latency and cost.

I reach for the claude-cookbooks caching examples when I need a reference implementation to show a client's engineering team exactly where to place the cache_control breakpoint in a multi-turn document Q&A setup.

python

import anthropic

client = anthropic.Anthropic()

# Simulate a large, stable policy document loaded once
policy_text = open('company_policy.txt').read()  # e.g. 6000 tokens

def ask_policy_question(user_question: str) -> str:
    response = client.messages.create(
        model='claude-opus-4-5',
        max_tokens=512,
        system=[
            {
                'type': 'text',
                'text': 'You are a compliance assistant. Answer only from the provided policy.',
            },
            {
                'type': 'text',
                'text': policy_text,
                'cache_control': {'type': 'ephemeral'},  # cache breakpoint
            },
        ],
        messages=[{'role': 'user', 'content': user_question}],
    )
    usage = response.usage
    print(f"Input: {usage.input_tokens} | Cache write: {usage.cache_creation_input_tokens} | Cache read: {usage.cache_read_input_tokens}")
    return response.content[0].text

print(ask_policy_question('What is the remote work reimbursement limit?'))
print(ask_policy_question('How many sick days are employees entitled to?'))
