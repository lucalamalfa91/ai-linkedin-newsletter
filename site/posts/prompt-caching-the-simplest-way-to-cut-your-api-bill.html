Prompt Caching: The Simplest Way to Cut Your API Bill

Most teams overpay on inference because they resend the same context on every call — here's how to stop.

November 4, 2026

A significant share of the inference cost I see in enterprise deployments comes from one habit: stuffing the same large system prompt, document corpus, or few-shot examples into every single API call, as if the model has never seen them before. At scale — say, a workflow that runs hundreds of times a day against the same policy documents — that's not a design decision, it's a billing problem. Anthropic's prompt caching lets you mark a prefix of your prompt as cacheable, and subsequent calls that share that prefix pay a fraction of the input token price. The cache hit rate on a well-structured workflow can push 90%+, and the latency drop on long prompts is noticeable too.

The catch is that cache keys are positional and exact. If anything before the cache_control breakpoint changes between calls — even whitespace — you get a cache miss and pay full price. This means you have to think structurally about your prompt: stable content (instructions, reference documents, examples) goes first and gets marked for caching; dynamic content (the user's actual query, runtime variables) goes last. It's a discipline most teams don't apply until they see the invoice.

Notice what the usage numbers show on the second call: 3,889 tokens served from cache at roughly 10% of the normal input price, and only 312 new tokens billed at full rate. That ratio improves further as you add more calls in the same session. The structural lesson from the financial agent work that's become common in enterprise settings — where the same context window persists across dozens of model calls over hours or days — is that caching isn't a micro-optimization. It's the difference between an agentic workflow that's economically viable and one that quietly costs a fortune to run.
