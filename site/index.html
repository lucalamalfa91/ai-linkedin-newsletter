#2 Simon Willison ★ 5/10

sqlite-utils 4.0rc1 adds migrations and nested transactions

June 21, 2026

↳ WHAT'S NEW sqlite-utils 4.0rc1 ships two long-requested features: a migrations system and nested transaction support. The library, maintained by Simon Willison, wraps Python's sqlite3 module with higher-level operations for both programmatic and CLI use. ↳ THE REAL STORY Migrations mean you can now version-control schema changes inside sqlite-utils workflows without reaching for a separate tool like Alembic or writing raw ALTER TABLE logic by hand. Nested transactions (implemented via SQLite's SAVEPOINT under the hood) let you wrap operations that already use transactions without blowing up — useful when composing library calls that each manage their own transaction boundaries. For anyone building data pipelines or CLI tools on top of SQLite, these two additions close the gap between sqlite-utils and heavier ORMs for day-to-day schema management.

Claude's take

This is an rc1, not a final release — the migrations API in particular is worth scrutinizing before building against it, since migration systems are notoriously hard to change once people depend on them. The bigger question is how opinionated the migration format turns out to be: if it ties you to sqlite-utils' own conventions, mixing it with other tools (Datasette, raw sqlite3, or anything that writes to the same file) could get messy. Worth reading the actual API docs before adopting it in production pipelines.

#3 GitHub ★ 5/10

sqlite-utils 4.0rc1

June 21, 2026

↳ WHAT'S NEW sqlite-utils 4.0rc1 ships two headline additions: a migrations system and nested transaction support. This is the first release candidate for the major version bump of Simon Willison's Python library for scripting SQLite databases. ↳ THE REAL STORY Migrations mean you can now track and apply schema changes programmatically within sqlite-utils itself — previously you'd bolt on a separate tool or hand-roll version tracking. Nested transactions (via SAVEPOINTs under the hood) let you wrap operations inside an already-open transaction without blowing it up on rollback, which matters when you're composing functions that each want transactional safety. For anyone using sqlite-utils as the persistence layer in data pipelines or CLI tools, both features reduce the amount of glue code you write around the library.

Claude's take

This is an rc1 on a major version, so the API surface for migrations in particular is worth scrutinizing before you build against it — breaking changes between rc1 and final are still on the table. The bigger question is whether the migrations design is opinionated enough to be useful or flexible enough to not get in the way: SQLite schema migrations are notoriously awkward (no DROP COLUMN before SQLite 3.35, limited ALTER TABLE), and how sqlite-utils handles those edge cases will determine whether this replaces Alembic-lite setups or just adds a new abstraction to learn.
