#3 GitHub

Dependabot version updates introduce default package cooldown

July 14, 2026

↳ WHAT'S NEW Dependabot version updates now include a built-in 3-day cooldown period before opening a pull request for any new package release. No configuration required — it applies by default across all repos using Dependabot. ↳ THE REAL STORY This is a direct response to supply chain attacks like the one that hit `tj-actions` earlier this year, where a compromised package was published and rapidly pulled into thousands of repos via automated PRs before anyone noticed. The 3-day window gives the ecosystem time to catch malicious or broken releases before they land in your dependency tree. In practice, teams running Dependabot on active repos will see fewer same-day PRs for patch and minor bumps — which also means less noise in the PR queue without any manual tuning.

Claude's take

The catch is that three days is an arbitrary number that won't stop a patient attacker, and it creates a false sense of security. A malicious package that stays live for 72 hours — which many do — still gets through. More importantly, for teams that *want* fast dependency updates (security patches, zero-days), there's no mention yet of an opt-out or a per-package override to bypass the cooldown. If that configurability doesn't exist, you're trading automation speed for a security theater buffer on the exact updates where speed matters most.

#5 Lobsters

lobste.rs is now running on SQLite

July 14, 2026

↳ WHAT'S NEW Lobsters, the developer-focused link aggregation site, completed a migration from MariaDB to SQLite in production — a move that had been in planning since 2018, originally targeting PostgreSQL before pivoting to SQLite. ↳ THE REAL STORY This is a real-world data point for the "SQLite in production" debate. Lobsters is a live, multi-user web app with concurrent reads and writes, not a toy project. The fact that a Rails app serving a developer community can run comfortably on SQLite challenges the default assumption that any serious web app needs a client-server database. For developers building small-to-medium Rails or Django apps, this is evidence — not just theory — that SQLite's WAL mode and modern hosting (single-server, NVMe) can handle the load without the operational overhead of managing a separate database process.

Claude's take

The catch is that Lobsters is a low-write, read-heavy site with a single-server deployment — conditions that happen to be SQLite's sweet spot. The moment you need horizontal scaling, read replicas, or cross-region replication, this architecture hits a wall. The more interesting open question: as Litestream, LiteFS, and Turso push SQLite toward distributed setups, how far can this model actually stretch before you're just reinventing the complexity you were trying to avoid?
