#1 GitHub ★ 6/10

DOOMQL

July 13, 2026

↳ WHAT'S NEW DOOMQL is a Doom-like game where SQLite is the game engine — not just storage. Movement, collision, rendering logic all run as SQL queries. Built by Peter Gostev using GPT-4.5 (referred to in the source as GPT-5.6 Sol, likely o3/GPT-4.5 era tooling). ↳ THE REAL STORY This is a proof-of-concept that pushes SQL into territory it was never designed for: stateful, frame-by-frame game loop execution. Every tick — player position, raycasting, collision detection — is computed via SQL statements against SQLite tables. It works because SQLite is an in-process library with near-zero query overhead, making the absurd latency math just barely acceptable for a low-framerate game. For developers, the interesting part isn't the game itself but the architecture: it demonstrates that any sufficiently expressive query language can encode arbitrary state machines if you're willing to abuse it hard enough.

Claude's take

The real question this raises isn't 'can you do this' — clearly you can — but what it says about AI-assisted development. Gostev used a frontier model to write code that no sane developer would write by hand, in a paradigm that has essentially no prior art or Stack Overflow to lean on. That's the pattern worth tracking: LLMs making deliberately unreasonable architectural experiments cheap enough to actually attempt. The catch is that the output is also nearly unmaintainable by humans — you get a working curiosity, not a codebase anyone extends.

#2 Simon Willison ★ 4/10

Using uvx in GitHub Actions in a cache-friendly way

July 14, 2026

↳ WHAT'S NEW Simon Willison documented a cache-friendly pattern for using `uvx` in GitHub Actions by setting a `UV_EXCLUDE_NEWER` environment variable pinned to a specific date — preventing uv from fetching newer package versions and making the dependency resolution deterministic enough for cache hits. ↳ THE REAL STORY The core problem: `uvx` resolves packages at runtime, and without version pinning, GitHub Actions cache keys mismatch on every run that pulls a newer package version — effectively making the cache useless. Setting `UV_EXCLUDE_NEWER` to a fixed date freezes the resolution window, so the cache key stays stable across runs. For workflows that call `uvx` frequently (linting, formatting, one-off CLI tools), this can shave meaningful seconds off CI times without requiring a full lockfile or explicit version pinning in the workflow YAML.

Claude's take

The catch is maintenance overhead by stealth. A date-pinned `UV_EXCLUDE_NEWER` means you're silently drifting away from security patches and bug fixes in those tools — and unlike a dependabot-managed lockfile, there's no automated nudge to update it. Teams that set this and forget it could be running outdated versions of tools like `ruff` or `mypy` for months without noticing. Worth pairing with a calendar reminder or a periodic CI job that bumps the date deliberately.

Claude's take
